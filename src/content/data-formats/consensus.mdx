Our <AppLink
href="https://github.com/Blockchain-Technology-Lab/consensus-decentralization">consensus-decentralization</AppLink>
tool expects one file per ledger, named `<project_name>_raw_data.json` (e.g.
`bitcoin_raw_data.json`), in newline-delimited JSON — one JSON object per block,
per line. The entries in the file should adhere to the following format:

```json
{
  "number": "<block number>",
  "timestamp": "<yyyy-mm-dd hh:mm:ss UTC>",
  "identifiers": "<some identifier linking the block to its creator, such as  Bitcoin's coinbase_param field, Ethereum's extra_data field, or Cardano's pool_ticker field>"
  "reward_addresses": ["<address(es) that received the block reward, comma-separated if there are multiple>"]
}
```

Every entry's `timestamp` is UTC. Most ledgers format it as `yyyy-mm-dd hh:mm:ss UTC`; some raw samples (e.g. Cardano) use ISO 8601 (`yyyy-mm-ddThh:mm:ss`, no suffix) instead — either is fine, so just match whatever your own node/crawler naturally produces.

If some field is not applicable for a specific blockchain, then it can be
omitted, but ideally we want all of them to be included.

## Mapping information

If you also have information linking block identifiers or reward addresses to
the real-world entities that control them (e.g. mining pools), you can share
that too. This mapping information falls into three categories: identifiers,
addresses and legal links. Full details are available on the <AppLink
href="https://blockchain-technology-lab.github.io/consensus-decentralization/mappings/">mappings
documentation page</AppLink>.

**Identifiers** link a pool's tag or ticker, the substring by which it is
identifiable in the blocks it produces — to information about the pool, such
as its name and homepage. As with raw data, this is one file per ledger,
named `<project_name>.json` (e.g. `bitcoin.json`):

```json
{
  "P1": {
    "name": "Pool P1",
    "homepage": "example.com/p1"
  },
  "--P2--": {
    "name": "Pool P2",
    "homepage": "example.com/p2"
  }
}
```

**Addresses** link a reward address to the pool that owns it, along with a
public source for the ownership claim. Again, one file per ledger, named
`<project_name>.json` (e.g. `bitcoin.json`):

```json
{
  "address1": {
    "name": "Pool P2",
    "source": "example.com"
  }
}
```

**Legal links** record off-chain ownership relationships between a pool and
its parent company (e.g. following an acquisition), so that blocks can be
attributed to the top-level entity that ultimately controls the pool. Unlike
identifiers and addresses, this is a single file, `legal_links.json`,
covering all ledgers:

```json
{
  "<parent company>": [
    {
      "name": "<pool name>",
      "from": "<start date>",
      "to": "<end date>",
      "source": "<source of information>"
    }
  ]
}
```
